Mysql事务

发表于 2026-09-22 更新于 2026-09-24 分类于 疯狂八股 ， Mysql 阅读次数： 本文字数： 5k 阅读时长 ≈ 9 分钟

Mysql中的事务指的是一组要么全部成功要么全部失败的数据库操作，来保证数据的正确，试想一下在一个电商的支付场景下，若是用户已经成功支付且支付回调也正常，但在将订单状态从待支付修改到待发货时数据库突然出现错误导致状态未修改，就等于用户花钱买到了空气。这显然是无法接受的，这时候就需要事务出场了，当数据库报错时应回滚用户的支付并返回支付失败，对数据库来说就像这次操作并未发生过一样。

0.MySQL日志

由于MySQL的事务是由日志实现的，所以在具体介绍事务之前，先简单了解一下日志的原理，在MySQL中主要使用的日志有binlog(mysqlServer生成，哪个引擎都支持)，redo_log，undo_log（存储引擎实现，InnoDB使用）

0.1 binlog归档日志g

binlog是Server层的产物，当MySQL每完成一条更新操作，就会生成一条binlog日志当事务完成后统一写入binlog文件，每一条binlog里根据模式记录了这次操作的SQL语句或操作变更前后的数据行或二者混合记录（根据SQL是否安全判断如何记录）。总的来说就相当于数据库的备份，放在当数据库发生错误时间产生数据丢失。除了此之外在MySQL主从复制中binlog还负责从从主库像从库传递数据更新，当发生数据更新时，主库就像从库发生binlog文件，从库接收后放到缓冲队列，然后队列顺序重放binlog来达到数据同步的效果。

总结一下binlog的主要作用就是1.保证数据的持久化。2.实现主从复制

0.2 redo_log重做日志

在InnoDB引擎修改数据时不是直接将修改后的内容直接写到磁盘里的，而是先写到一个缓冲池Buffer Pool里，等下一次有查询访问这个数据就可以直接返回用于提高数据库的读写性能，但是这就存在一个问题，要缓冲池里的内容还没写入磁盘前系统发生崩溃或机器停电等问题，导致内存里的数据丢失，那意味着磁盘内存的是未被更新旧数据。redo_log就是为了解决这个问题的。每当有一条记录更新时InnoDB会先将本次修改以redo_log的形式记录下来后更新Buffer pool里的脏页，这次更新才算完成。后续InnoDB会在合适的时间将缓冲池里的脏页刷新到磁盘里。

在redo_log的具体实现上，redo_log本质是一个物理日志，记录对某个数据页进行了什么修改，例如对xxx表空间的yyy数据页zzz偏移量的地方做了AAA更新。不记录行数据。redo_log是存储在磁盘上的在事务提交时需要将记录好的redo写入redo log 文件这样事务才算提交成功。redo_log文件可存储在OS page cache（内存空间）里，具体的刷盘时间InnoDB提供了三种策略，由一个参数控制

  • 当参数为0时，每次事务提交时，将redo log留在redo log buffer（内存）里，该模式下事务提交时不会主动触发写入磁盘操作，由InnoDB的后台线程每隔一秒将redo log buffer里的redo log写入Page Cache后持久化到磁盘
  • 当参数为1时，每次事务提交时，都会将缓存在redo log buffer里的redo log直接刷到磁盘里
  • 当参数为2时，每次提交事务时，只会将redo log buffer里的redo log写入redo log文件（不一定在磁盘），落到操作系统的page cache里等于由操作系统决定什么时间进行刷盘操作。一样的每秒都将Page Cache里的redo log 持久化到磁盘。

总结一下在安全性上当发生故障时0会丢失过去1s的数据，1不会发生丢失，2只有在操作系统崩溃时才会丢失过去1s的数据。在效率上，0将redo log只写入redo log buffer，1直接将redo log写入磁盘，2将redo log写入redo log buffer后再提交时写入Page Cache。

三者的关系为：

数据安全性：1 > 2 > 0

写入性能：0 > 2 > 1

redo_log的具体存储结构说两个连起来的环形数组，当脏页从缓冲池刷入磁盘后对应的redo_log旧日志就可以被覆盖了，整个环形数组是按时顺时针方向来进行覆盖的一个指针指向可以写入位置，一个指针指向检查位置（当前指向脏页是否被写入）二者在顺时针方向的间隔就是剩余可用写入的空间

0.3undo_log回滚日志

undo_log是用来实现事务的原子性的，在事务开始后的第一条更新操作执行前会创建undo_log来记录事务执行前的数据信息。若事务提交前发生崩溃或出现错误，就根据undo_log将数据回滚到事务执行前的状态，以此来实现原子性。

在具体的实现上，undo_log不是在事务开始时就创建的而是在事务中每条数据更新时创建一个undo_record，同时在表中不显示的列里记录此次操作对应事务trx_id(这个列在后面MVCC实现扮演着重要的角色）和回滚数据行的指针roll_pointer。

undo log 存在回收机制，当前的undo log若不在被Read View需要（就是所有的活跃事务的最小trx_id都已经大于当前undo log的trx_id版本了）这个undolog就会被回收

总结一下undo_log的主要作用：

  1. 实现事务回滚，保证事务的原子性
  2. 实现MVCC的关键因素之一，间接保证事务的隔离性

1.事务的特性

在Mysql中事务是由存储引擎来实现的，常见的InnoDB引擎就支持事务操作，事务的定义看起来简单但要实现事务操作就必须要遵守四个特性

  1. 原子性

    就像定义一样一个事务内的操作要么全部成功要么全部失败，使整个事务像原子一样不可分割。 原子性由undo_log实现

  2. 持久性

    事务结束后对数据的修改就是永久性的即使系统故障也不会丢失修改。持久性由redo_log实现

  3. 一致性

    这个比较抽象，指的是事务操作前和操作后数据满足完整的约束性，例如A给B200块在事务结束后 A = A - 200,B = B + 200。一致性由原子性+隔离性+持久性共同保证。

  4. 隔离性

    如果数据库在执行事务时是串行的那很影响数据库的执行效率，所以数据库是允许多个并发事务同时执行对数据的读写和修改，但这导致多个事务若同时读写一个数据就会出现脏数据的情况，所以就引入隔离性来保证多个事务交叉执行带来数据干扰。隔离性由MVCC实现。

关于原子性和持久性的对应实现原理，都在前面的日志部分已经说过。只有事务的隔离性MVCC的实现没有展开了解，下面就展开看一下MVCC的原理

2.事务的隔离性

在了解MVCC之前先要知道并行事务可能会引发什么错误，因为事务隔离性的等级就是根据对应的错误进行处理的。

  1. 脏读

    如果一个事务读到了另一个未提交的事务修改过的数据，就说明发生了脏读。在个人理解上感觉脏读就是读操作完全未做任何隔离只受行锁影响导致的，事务可以在随意的读取数据

  2. 不可重复读

    在一个事务内多次读取同一个数据，如果出现前后两次读到的数据不一样的情况，就意味着发生了不可重复读。这个个人理解就是在事务执行的时候每次都读最新的数据同时有别的事务可以对该数据进行写操作导致。

  3. 幻读

    在一个事务内多次查询某个符合条件的记录数量，如果出现前后不一致的情况就意味着发生了幻读。个人理解幻读的原因是虽然在每次读的时候都是读的事务开始的版本借此屏蔽了其他事务写操作带来的影响，但是若是插入了一条新的数据后再进行查询时仍会读到这条数据这就会导致前后数量的不一致，而不是数据内容的不一致。

根据这个三个错误，SQL标准又将事务的隔离性又划分为四个等级

  1. 读未提交，指一个事务还么提交时，它的变更就能被其他事务看见，此隔离性下可能发生脏读、不可重复读和幻读。
  2. 读提交，指一个事务提交后他做的变更才能被其他事务看到，此隔离性下可能发生不可重复读和幻读。
  3. 可重复读，指一个事务执行过程中它看到的数据一直和这个事务启动时是一样的，此隔离性下可能发生幻读。
  4. 串行化，指会对记录加上读写锁，只有上一个事务执行完了之后后续事务才能访问，此隔离性下不会出现错误。

因为，串行化等于将并行事务压缩成了串行这大大降低的效率，所以MySQL InnoDB引擎默认使用的可重复读的隔离级别，为了解决幻读问题提供了针对快照读和针对当前读两种解决方案。

2.1针对快照读（MVCC）

针对快照读的是通过MVCC来实现的，在事务启动时生成Read View其本质是一个数据快照，内部存储四个核心字段。

  • creator_trx_id：创建该事务的事务Id
  • m_ids：创建Read View时当前数据库中活跃且未提交的事务id列表
  • min_trx_id：创建Read View时当前数据库中活跃且未提交的最小事务id
  • max_trx_id：创建Read View时当前数据库中应该给下一个事务的id值

Read View再MVCC中具体的使用还依赖前文提到的每行数据的隐藏列里的trx_id，记录此数据上一次被写操作的事务id，通过与Read View比较来判断是否该数据是否对当前事务可见。

  • trx_id < min_trx_id：这意味着上一个修改条数据的事务已经结束，此条数据对当前事务可见
  • trx >= max_trx_id：着意味着这个条数据是在当前事务创建过后又被修改过的了，要根据undo log版本链回溯，直至找到可见版本
  • min_trx_id<=trx_id < max_trx_id：这说明这条数据上一次修改的事务是在当前事务创建前就已经启动但不知到有没有提交，这时要查询Read View里的m_ids字段，查看trx_id是否在里面（或者说还是否活跃）若不在则说明事务已经提交，当前数据可见。若在则说明事务尚未提交，当前版本数据不可见需要回溯判断。

这种通过控制链回溯来控制并发事务访问同一个记录的行为就叫MVCC（多版本并发控制），但MVCC只解决了快照读的幻读问题，缺无法解决当前读，想象一个场景，数据表里有id为3，5的两条数据，事务A查询id>1的数据，显然会搜索2条记录，这时事务B向表中插入了一条id为2的数据，事务A再次查询id>1的数据，搜索结果依然是2条。但事务A现在执行了一条更新id= 2的数据的SQL语句，此时id=2的这条数据的trx_id就会被更新为事务A的trx_id。事务A再次查询id>1的数据搜索到的记录就会变成3条。出现了幻读！很奇怪的但这种现象是会发生的，核心原因是MVCC只是看不见新插入的，但不会阻止写操作（写操作修改的物理版本而不是快照版本）所以导致事务A可以操作自己看不见的数据的。出现幻读现象。

2.2针对当前读

InnoDB为了解决当前读的幻读问题，提供的解决方法是next-key lock(行锁+间隙锁)临键锁。想要更好的理解next-key lock，就要先了解这些锁的含义。

  • 行锁：只锁索引上存在的某一条记录
  • 间隙锁：锁住索引间的空隙，不锁记录本身。主要目的是阻止别的事务在这个间隙插入新数据（间隙锁只阻塞插入）。间隙是左开右开。
  • 临键锁：即next-key lock，本质是行锁+间隙锁，锁住的是目标索引记录+它左边的间隙，所以是左开右闭的。

看上述锁的定义可以知道，索引间的间隙是维持锁的关键，这个间隙是在上锁的那一刻将索引排序后每两个相邻的索引间就是一个间隙。比如索引有1 3 5那间隙就是(-∞,1]、(1,3]、(3,5]、(5,+∞)。还有一点注意的是临键锁不是任何时候都加的，当出现主键等值查询且这条记录真实存在只加行锁，等值查询，索引找不到匹配记录，只加间隙锁。

快照读和当前读解决幻读的方式是不一样的所以适用范围也不一样，针对快照读的事务id那套东西并不太适用于当前读的场景，控制当前读是否可主要就是锁机制。简单来说当事务A对某行事务执行操作时就会根据类型对索引加上对应的锁（锁是加载索引上，若不走索引锁就会退化成表锁），这把锁会阻碍其他事务对当前数据或当前数据的索引间隙执行写操作，知道当前事务提交对锁进行释放。

现在我们再回到MVCC无法解决的场景。当事务A启动后先执行id > 1的带锁查询操作，间隙锁锁住（1，+∞），此时事务B想要向事务A查询的范围内插入数据因为事务A尚未提交，事务B就会因为间隙锁而陷入阻塞状态，直到事务A提交后才会完成这次插入。但此时事务A早已提交就不会有幻读的风险。
