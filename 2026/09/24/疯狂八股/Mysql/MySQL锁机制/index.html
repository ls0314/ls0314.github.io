MySQL锁机制

发表于 2026-09-24 更新于 2026-09-25 分类于 疯狂八股 ， Mysql 阅读次数： 本文字数： 3.1k 阅读时长 ≈ 6 分钟

1.MySQL的锁分类

锁机制其实很好理解再各种语言和中间件里都存在，核心就是保证一个正在被某个角色/事务修改的数据不会被其他角色/事务修改。在MySQL里就是正在被事务修改的数据行/表/库不会被修改。而MySQL中按照锁的的等级分为全局锁，表级锁和全局锁，下面按照这个顺序分别介绍一下。

1.1全局锁

全局锁的使用方式是 flush tables with read lock。 当执行后整个数据库就会变成只读状态，不会发生数据修改，所以的写操作都会被阻塞。想要释放的话就执行 unlock tables或断开数据库连接也会自然释放。这个锁看着很夸张全局阻塞所以写操作，但用在数据库备份上就很适合了，全局阻塞在备份期间就不会有新数据写入导致备份和主库不一致。当然这也会带来许多缺点因为变成只读数据库，那业务的写操作就会被阻塞造成业务停滞。

当然也有方法解决这个问题，就是不使用全局锁。在支持可重复读事务的存储引擎，可以在备份数据库之前开启事务先创建Read View，因为在不加临键锁的情况下数据库是允许写入操作的且整个数据库都被Read View快照，可以凭此进行备份操作。

1.2 表级锁

MySQL中表级锁主要有以下几类，我分别介绍一下如何使用和具体的使用场景

  • 表锁：顾名思义就是锁住整个表，显示的阻塞其他进程对这个表的读/写操作，直至锁释放。需要注意的是如果SQL声明了某线程只能对某个表进行读/写操作，那它就只能对这个表进行读/写操作，而不能操作其他表同时其他线程也不能锁住的表进行写操作。其具体使用场景有当间隙锁没作用在索引上时会逐行锁住全表等价于表锁。

  • 元数据锁（MDL）：这个锁主要是包含数据表的结构的，保证当有线程对表进行读/写操作是阻塞其他线程对表的结构进行修改（增加/删除字段）。这个锁不需要显示的使用，当对数据库表进行操作时会自动的给表加上MDL。对数据库表进行CRUD时加的是MDL读锁，对数据库表进行结构操作时加的是MDL写锁。当事务提交后MDL自动释放。

  • 意向锁：理解这个锁之前应先了解行锁，所以这块就记住一点。意向锁是表级的辅助锁，为了快速判断目标表有没有行锁避免全表扫描，意向锁之间兼容，和表锁互斥。

  • AUTO-INC锁：因为常用的数据库表主键都是自增类型，所以我们很自然的希望同一个SQL插入的数据是连续的，为了保证在SQL执行插入时不会被别的写操作抢走自增值，就要使用AUTO-INC也就是自增锁。自增锁为了平衡自增连续性和插入的效率有两种上锁的方式，分别是给当前字段赋完自增值就释放，不等到事务结束（轻量级锁）和等事务结束（AUTO-INC)在释放。根据这两个方法InnoDB提供三种模式使用innodb_autoinc_lock_mode控制（下面简称为mode）

    mode == 0 采用纯AUTO-INC锁，事务结束才释放。

    mode == 2 采用纯轻量级锁，申请了自增主键后就释放。（有个弊端是当搭配的binlog格式是statement时可能出现主从不一致的情况）

    mode == 1 分为两种情况若插入的SQL语句可以提前知道插入行锁就使用轻量级锁，若是使用批量插入不知道插入行数就使用AUTO-INC锁。

1.3行级锁

其实行级锁在介绍数据库事务时已经基本提到了，大致分为行锁（记录锁）、Gap Lock（间隙锁）、Next-Key Lock（临键锁）和一个插入意向锁。在具体介绍行级锁之前先，了解一个小概念，共享锁（s锁）读读共享，读写互斥。独占锁（x锁）写写互斥、读写互斥。而且行级锁都是加在索引上的所以下述的间隙、记录等描述都是针对索引的。

  1. 行锁：也叫记录锁，其锁住的一条索引记录。有上述的S/X锁之分。事务提交后释放
  2. Gap Lock：间隙锁，在事务里介绍过其锁住的是一个索引间隙。目的是为了解决幻读的现象也可以理解为范围锁。间隙锁之间是兼容的，两个事务可以共同的持有包含公共间隙范围的间隙锁不会产生互斥。因为间隙锁的目的是阻止被锁住的范围有数据插入，那么被一个事务阻止还是被n个事务阻止是没区别的。
  3. Next-Key Lock：临键锁，本质是行锁+间隙锁。因为间隙锁是（）的只能阻止间隙的数据插入不能包含已有数据的修改所以在间隙锁的基础上加上行锁变成（]不仅保护索引间隙还包含具体的索引记录
  4. 插入意向锁：与表级的意向锁名字相似但作用完全不同，表级的意向锁核心作用是当事务向给表的某些行加S/X锁时提前打标记快速判断表冲突的。但插入意向锁本质更像是一个变种的间隙锁，锁住的是一个被间隙锁阻止插入的行，等间隙锁解除后保证可以第一时间写入。同时将被间隙锁阻塞的串行队伍变成并行队伍各自事务拿自己对应行的插入意向锁。

2.MySQL行级锁使用规则

行级锁的加锁形式根据不同的场景而变化的，但是有基本的规则：加锁的对象是索引，加锁的基本单位是临键锁。但是在某些情况下临键锁可能会退化为间隙锁或记录锁这就导致了行级锁随场景变换。下面介绍几种会退化的情况

  1. 唯一索引（主键索引）等值查询，若查询记录存在退化为记录锁，若不存在退化为间隙锁
  2. 唯一索引（主键索引）范围查询，在对唯一索引进行范围查询时会对每一个扫描到符合范围的索引加临键锁，只有遇到特殊情况时才会退化
    • 针对大于等于，因为还存在一个等值查询所以若那个边界的等值查询存在那么边界索引的锁就会退化为记录锁
    • 针对小于或小于等于，依然是看边界值是否存在表中，若不在拿小于等于和小于都会将边界的临键锁退化为间隙锁。若存在则只有小于会将临键锁退化为间隙锁。
    • 为什么会出现上述这种情况呢?其是本质上还临键锁左开右闭的特性导致的，因为当范围查询时大于方向是边界可能存在等值查询的值落在开区间所以只需要判断边界值存在是否要退化为记录锁来保证锁的范围覆盖；而范围查询是小于方向边界可能存在的等值查询会落到闭区间天然锁区间覆盖，现在要判断的就是边界值存在要不要覆盖，若不覆盖就退化为间隙锁左开右开即可。
  3. 非唯一索引等值查询，针对非唯一等值查询会对二级索引和当满足搜索条件时向对应的主键索引加锁，然后若查询值存在对每一个符合条件的查询值加的是记录锁/行锁，对第一个不符合的索引记录加间隙锁；若不存在对第一个大于查询值的索引记录加间隙锁，保证此条索引不会被临键锁锁住。
  4. 非唯一索引范围查询，二级索引都加临键锁，主键索引只加记录锁
  5. 没有使用索引的查询，因为没有使用索引导致是走的全表扫描，所以会逐个主键索引加临键锁，等同于加了一个表锁。

3.死锁

在InnoDB引擎里间隙锁是共享的，这意味着同一个间隙可能会被不同事务的间隙锁锁住，想象一下现在数据库表中有1，3，5三个索引，事务A开启当前读查询索引为6的的行此时会事务A锁住（5，+），在事务A进行下一步插入之前，事务B也开启当前读查询索引为7的是否存在此时事务B将（5，+）也锁住。这就形成一个死锁，当事务A要插入6时发现（5，+）被事务B锁住，事务B想要插入7时发现（5，+）被事务A锁住。二者互相阻止程序就会僵在这。

如何避免死锁？ 死锁有四个必要条件：互斥、占有且等待、不可强占用、循环等待。只要死锁出现那这些条件必成立，反之来说这些条件任意不满足就不会出现锁。在数据库层面有两种策略通过打破循环等待条件来解除死锁状态：

  • 设置事务等待锁的超时时间：当一个事务的等待时间超过该值后，就对这个事务进行回滚，于是锁就释放了，另一个事务就可以继续执行了。在 InnoDB 中，参数 innodb_lock_wait_timeout 是用来设置超时时间的，默认值时 50 秒。
  • 开启主动死锁检测：主动死锁检测在发现死锁后，主动回滚死锁链条中的某一个事务，让其他事务得以继续执行。将参数 innodb_deadlock_detect 设置为 on，表示开启这个逻辑，默认就开启。
